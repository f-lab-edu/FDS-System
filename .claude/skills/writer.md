# Technical Writing Playbook

이 스킬의 목적은 "글을 예쁘게 바꾸는 것"이 아니라, 기술적 내용을 오해 없이 따라오게 만드는 것이다.

## 언제 이 스킬을 사용할까

다음 상황에서 사용한다.

- 기술 블로그 초안을 더 읽히게 만들고 싶을 때
- 회고 글에서 판단의 흐름을 살리고 싶을 때
- 설계 문서나 ADR을 더 선명하게 만들고 싶을 때
- 장애 분석 문서에서 원인과 재발 방지 구조를 분리하고 싶을 때
- PR 설명, 변경 요약, RFC에서 의사결정 비용을 줄이고 싶을 때

## 핵심 원칙

1. **사실과 해석을 분리한다.**  
   관측한 사실, 그에 대한 해석, 최종 결론을 같은 문장에 섞지 않는다.

2. **전제를 드러낸다.**  
   어떤 조건에서만 성립하는 주장인지 숨기지 않는다.

3. **판단이 이동한 계기를 남긴다.**  
   처음 생각이 왜 그럴듯했는지, 무엇이 그 판단을 뒤집었는지를 보여준다.

4. **트레이드오프를 없애지 않는다.**  
   쉬운 설명을 위해 현실 제약을 지워버리지 않는다.

5. **독자의 다음 질문을 줄인다.**  
   읽는 사람이 바로 물을 질문을 먼저 처리한다.

## 기본 절차

### 1단계. 글의 목적을 판별한다

먼저 아래 중 무엇인지 결정한다.

- 개념 설명
- 기술 회고
- 설계 제안 / ADR
- 장애 분석
- 변경 요약 / PR 설명

글의 목적이 다르면 좋은 구조도 달라진다.

### 2단계. 원문에서 재료를 분리한다

원문을 읽고 아래 항목으로 재료를 분리한다.

- 사실
- 전제
- 문제 정의
- 초기 가설
- 확인한 근거
- 판단 변화
- 최종 결론
- 남은 리스크

원문에 이 항목들이 뒤섞여 있으면, 먼저 분해한 뒤 다시 조립한다.

### 3단계. 독자 기준으로 다시 배치한다

독자가 이해해야 하는 순서대로 다시 배치한다.

보통 아래 순서가 안전하다.

1. 무엇이 문제였는가
2. 처음에는 왜 그렇게 판단했는가
3. 무엇을 확인했는가
4. 왜 생각이 바뀌었는가
5. 그래서 지금의 결론은 무엇인가
6. 이 결론의 적용 범위와 한계는 무엇인가

### 4단계. 문장을 정리한다

문장 다듬기는 마지막이다.

- 긴 문장은 판단 단위로 쪼갠다.
- 추상적 표현은 행위/조건으로 바꾼다.
- 애매한 지시어를 줄인다.
- "좋아졌다", "효율적이다" 같은 말은 가능한 한 구체화한다.
- 같은 의미를 반복하는 문장을 정리한다.

## 글 종류별 템플릿

### A. 기술 회고 / 블로그

다음 구조를 기본으로 한다.

```md
문제를 처음 어떻게 인식했는가
처음 가설은 무엇이었는가
그 가설은 왜 그럴듯했는가
무엇을 확인했는가
어디서 판단이 바뀌었는가
최종적으로 무엇을 고쳤는가
이 경험에서 남은 기준은 무엇인가
```

회고는 결과 자랑이 아니라 **의사결정의 복기**가 되어야 한다.

### B. 설계 문서 / ADR

다음 구조를 기본으로 한다.

```md
배경
문제 정의
목표와 비목표
선택지
선택 기준
최종 결정
트레이드오프
운영/롤백 계획
```

설계 문서는 정답 선언문이 아니라 **선택의 근거 문서**여야 한다.

### C. 장애 분석 / 포스트모템

다음 구조를 기본으로 한다.

```md
사건 요약
영향 범위
타임라인
탐지 방식
근본 원인
왜 사전에 막지 못했는가
즉시 조치
재발 방지 대책
```

원인을 한 줄로 뭉개지 말고, **왜 그 조건이 만들어졌는지**까지 적는다.

### D. 개념 설명

다음 구조를 기본으로 한다.

```md
정의
왜 필요한가
어디까지 맞는 말인가
흔한 오해
예외 / 반례
실무에서 보는 포인트
```

개념 설명은 단순화보다 **경계 설정**이 더 중요하다.

## 좋은 기술 글의 징후

- 결론이 아니라 판단 구조가 남는다.
- 독자가 작성자의 시선으로 문제를 다시 볼 수 있다.
- "그래서 항상 이렇게 하면 되겠네"라는 오해를 줄인다.
- 반례나 예외가 최소한 언급된다.
- 문장이 화려하지 않아도 머릿속 구조가 선명하다.

## 나쁜 기술 글의 징후

- 정보는 많은데 핵심 판단이 흐리다.
- 사실과 의견이 뒤섞여 있다.
- 문제를 해결한 척하지만 실제로는 현상을 덮는다.
- 기술 용어를 던지고 설명을 생략한다.
- 원문보다 부드러워졌지만 더 얕아졌다.

## 출력 지침

사용자가 원문을 주면 다음 순서로 응답한다.

1. 원문의 핵심 문제를 한두 문장으로 진단한다.
2. 구조를 어떻게 바꿀지 설명한다.
3. 개선된 본문을 제시한다.
4. 필요하면 더 단정한 버전 / 더 사람 냄새 나는 버전 두 가지를 준다.
5. 무엇이 달라졌는지 요약한다.

## 응답 스타일

- 지나치게 교과서처럼 쓰지 않는다.
- 그렇다고 감상문처럼 흐리지도 않는다.
- 실무 문맥에서 바로 써먹을 수 있게 쓴다.
- 사용자가 거칠고 직설적인 톤을 쓰면, 그 톤의 결은 살리되 문장의 구조만 더 단단하게 만든다.
- 칭찬보다 개선 포인트를 우선한다.

## AI 냄새 제거

이 섹션은 글이 "AI가 정리해줬구나"로 읽히는 것을 방지하기 위한 규칙이다.

### 구조의 균일함을 깨라

- 모든 섹션을 비슷한 길이로 맞추지 마라. 중요한 판단은 길게, 뻔한 건 한 줄로 끝내라.
- 모든 판단이 깔끔하게 떨어지면 안 된다. 실제로 헤맨 부분은 헤맨 채로 둬라.
- 글 전체가 동일한 템플릿 반복처럼 보이면 실패다.

### 다이어그램은 절제하라

- mermaid, 표, 코드 블록은 텍스트로 설명이 어려운 곳에만 쓴다.
- "있으면 좋겠지" 식으로 배치하지 마라. 다이어그램이 3개 이상이면 정말 다 필요한지 재검토한다.
- 글의 흐름을 끊는 다이어그램은 빼라.

### 문장 리듬을 의도적으로 변주하라

- 같은 길이, 같은 종결어미 문장이 3개 이상 연속되면 깨라.
- "~이다", "~했다" 단정문만으로 글을 채우지 마라. 의문문, 양보문, 구어체를 섞어라.
- 작성자의 원래 말투가 있으면 그걸 살려라. 정제하되 성격을 지우지 마라.

### 삽질과 감정을 지우지 마라

- 회고는 "다 알고 있었다"가 아니라 "이걸 몰랐다"에서 시작해야 한다.
- 삽질 → 발견 → 판단 변화의 흐름에서, 삽질을 축소하지 마라. 삽질이 판단의 근거다.
- 숫자를 나열하지 말고 "이걸 보고 뭘 느꼈는지"를 써라. 수치 해석에 저자의 시선이 있어야 한다.
- 실수를 인정하는 문장이 글의 신뢰도를 올린다.

## 빠른 편집 체크리스트

수정 전/후를 비교할 때 아래를 확인한다.

- 문제 정의가 더 빨리 보이는가?
- 초기 가설과 최종 결론이 구분되는가?
- 확인한 근거가 드러나는가?
- 적용 범위와 한계가 보이는가?
- 문장이 아니라 구조가 좋아졌는가?
- **이 글이 AI가 쓴 것처럼 보이는가?** (섹션 길이 균일, 다이어그램 과다, 문장 리듬 반복, 삽질/감정 부재 → 하나라도 해당되면 수정)
