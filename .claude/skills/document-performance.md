# 요구사항 문서 작성 시 핑퐁을 줄이는 방법

## 문제 상황

요구사항을 받았을 때 바로 속성 정의, 비즈니스 규칙, 다이어그램으로 뛰어가면:
- 개발자와 여러 번 핑퐁하게 됨
- "이건 뭐지?", "이 케이스는?" 질문이 반복됨
- 결국 시나리오를 다시 물어보게 됨

## 해결책: 업무 시나리오를 먼저 작성한다

**다이어그램이나 속성 정의 전에, 반드시 업무 시나리오를 자연어로 먼저 작성한다.**

---

## 업무 시나리오 작성 원칙

### 1. 페르소나를 정의한다

| 페르소나 | 설명 |
|----------|------|
| 일반 회원 | 앱을 사용하는 고객 |
| 어드민 | 백오피스에서 관리하는 운영자 |

역할별로 이름을 붙이면 시나리오가 구체적이 된다.
- "사용자가 주문한다" (X)
- "민지가 앱에서 주문 버튼을 누른다" (O)

### 2. 시나리오는 소설처럼 쓴다

**포함해야 할 요소:**

```
배경: 왜 이 행동을 하게 되었나
액터: 누가
장소: 어디서 (앱? 백오피스? 어떤 화면?)
선행조건: 이 행동을 하기 위해 먼저 필요한 것
시나리오:
  1. 사용자가 어디를 클릭한다
  2. 화면에 무엇이 나타난다
  3. 사용자가 무엇을 입력한다
  4. 시스템이 어떻게 처리한다 (API, 트랜잭션, 상태 변화)
  5. 결과가 어떻게 보인다
예외 시나리오: 실패하면 어떻게 되나
결과: 최종 상태
```

### 3. 시스템 처리도 구체적으로 쓴다

**나쁜 예:**
> 시스템이 주문을 생성한다.

**좋은 예:**
> 시스템 처리:
> - `POST /api/v1/orders` 호출
> - 트랜잭션 시작
> - 상품 재고 확인 (stock >= 주문수량)
> - 재고 차감: `UPDATE product SET stock = stock - 2 WHERE id = 201`
> - 주문 생성: Order (status: PENDING, totalAmount: 65000)
> - 주문 항목 생성: OrderItem (스냅샷 - productName, brandName, price)
> - 트랜잭션 커밋
> - 응답: 201 Created

### 4. 유비쿼터스 랭귀지를 사용한다

팀 전체가 같은 단어를 사용해야 한다.

| 이렇게 쓰지 말고 | 이렇게 쓴다 |
|-----------------|-----------|
| 아이템 | 상품 (Product) |
| 찜 | 좋아요 (Like) |
| 구매 | 주문 (Order) |
| 비활성화 | INACTIVE |
| 삭제 | Soft Delete (deletedAt 설정) |

**용어 사전을 먼저 정의하고 시나리오에서 일관되게 사용한다.**

### 5. 예외 시나리오도 반드시 작성한다

정상 흐름만 쓰면 안 된다. 예외 케이스가 설계의 핵심이다.

```
예외 시나리오 - 재고 부족:

1. 민지가 주문 확정을 누른다.
2. 시스템 처리:
   - 상품 A 재고(50) >= 주문수량(2) ✓
   - 상품 B 재고(0) >= 주문수량(1) ✗
   - 트랜잭션 롤백
   - 응답: 409 Conflict
     {
       "error": "STOCK_INSUFFICIENT",
       "message": "재고가 부족합니다",
       "details": [{ "productId": 105, "available": 0 }]
     }
3. 에러 메시지: "상품 B의 재고가 부족합니다"
```

## 작성 순서

### Phase 1: 용어 사전 (Ubiquitous Language)
- 도메인 용어를 정의한다
- 영문 매핑을 포함한다
- 팀 전체가 같은 단어를 쓰도록 한다

### Phase 2: 페르소나 정의
- 액터를 구체적인 인물로 만든다
- 역할, 배경, 목표를 정의한다

### Phase 3: 핵심 시나리오 작성
- 도메인별로 Happy Path를 먼저 쓴다
- 배경 → 액터 → 장소 → 선행조건 → 시나리오 → 결과
- 시스템 처리는 API, 트랜잭션, 상태 변화까지 포함

### Phase 4: 예외 시나리오 작성
- 각 시나리오의 실패 케이스를 추가한다
- 에러 응답과 사용자에게 보이는 메시지까지

### Phase 5: 시나리오 검증 질문
시나리오 작성 후, 다음을 자문한다:
- [ ] 이 시나리오를 읽고 개발자가 바로 구현할 수 있는가?
- [ ] 예외 케이스가 빠진 것은 없는가?
- [ ] 시스템 처리가 구체적인가? (API, 트랜잭션, 상태 변화)
- [ ] 용어가 일관되게 사용되었는가?

### Phase 6: 그 다음 다이어그램으로
시나리오가 충분히 명확해진 후에:
- 시퀀스 다이어그램 (핵심 흐름 2~3개만)
- 클래스 다이어그램 (도메인 모델)
- ERD (영속성)

## Anti-Patterns

### ❌ 시나리오 없이 바로 속성 정의로 가는 것
```
상품 속성:
- id: Long
- name: String
- price: Long
...
```
→ "그래서 이 상품을 언제 어떻게 쓰는 건데?" 질문이 나옴

### ❌ 시스템 처리를 생략하는 것
```
1. 사용자가 주문한다.
2. 주문이 완료된다.
```
→ "주문하면 재고는 어떻게 되는 거야?" 질문이 나옴

### ❌ 예외 시나리오를 생략하는 것
```
정상 흐름만 작성함
```
→ "재고 없으면 어떻게 해?" 질문이 나옴

### ❌ 용어를 일관되게 쓰지 않는 것
```
"상품을 찜한다" → "좋아요를 누른다" → "관심 등록한다"
```
→ "이게 다 같은 기능이야?" 혼란 발생

## 예시: 좋은 시나리오

```markdown
### 시나리오: 주문 생성

**배경**: 민지가 월급날을 맞아 찜해둔 상품들을 주문한다.

**액터**: 민지 (일반 회원, 로그인 상태)

**장소**: Loopers 모바일 앱 - 장바구니 화면

**선행조건**:
- 민지는 로그인 상태
- 장바구니에 상품이 담겨 있음
- 담긴 상품들의 재고가 충분함

**시나리오**:

1. 민지는 장바구니에 다음 상품을 담았다:
   - 핸드메이드 라벤더 캔들 (25,000원) × 2개
   - 감성 머그컵 (15,000원) × 1개

2. `주문하기` 버튼을 탭한다.

3. 주문 확인 화면이 나타난다:
   - 주문 상품 목록
   - 총 결제금액: 65,000원
   - [주문 확정] 버튼

4. `주문 확정` 버튼을 탭한다.

5. **시스템 처리**:
   - `POST /api/v1/orders`
   - Request: { items: [{ productId: 201, quantity: 2 }, { productId: 105, quantity: 1 }] }
   - 트랜잭션 시작
   - 상품 201 조회 → deletedAt IS NULL, stock(50) >= 2 ✓
   - 상품 105 조회 → deletedAt IS NULL, stock(100) >= 1 ✓
   - 재고 차감:
     - UPDATE product SET stock = stock - 2 WHERE id = 201 AND stock >= 2
     - UPDATE product SET stock = stock - 1 WHERE id = 105 AND stock >= 1
   - 주문 생성: Order (status: PENDING, totalAmount: 65000)
   - 주문 항목 생성 (스냅샷):
     - OrderItem (productName: "핸드메이드 라벤더 캔들", brandName: "달빛공방", price: 25000, quantity: 2)
     - OrderItem (productName: "감성 머그컵", brandName: "소소한하루", price: 15000, quantity: 1)
   - 트랜잭션 커밋
   - 응답: 201 Created

6. 주문 완료 화면이 나타난다:
   - "주문이 완료되었습니다!"
   - 주문번호, 주문일시 표시

**예외 시나리오 - 재고 부족**:

1. 민지가 `주문 확정`을 탭한다.
2. **시스템 처리**:
   - 상품 105 재고(0) < 주문수량(1)
   - 트랜잭션 롤백
   - 응답: 409 Conflict
     { "error": "STOCK_INSUFFICIENT", "details": [{ "productId": 105, "available": 0 }] }
3. 에러 메시지: "감성 머그컵의 재고가 부족합니다"

**결과**:
- 주문이 PENDING 상태로 생성됨
- 재고가 차감됨 (캔들: 50→48, 머그컵: 100→99)
- 스냅샷 저장됨 (나중에 상품 정보가 바뀌어도 주문 내역은 유지)
```

## 요약

| 순서 | 작업 | 목적 |
|------|------|------|
| 1 | 용어 사전 | 팀 전체가 같은 언어 사용 |
| 2 | 페르소나 | 시나리오를 구체적으로 만들기 |
| 3 | 업무 시나리오 | 도메인 이해 맞추기 |
| 4 | 예외 시나리오 | 엣지 케이스 커버 |
| 5 | 검증 | 개발자가 바로 구현 가능한지 확인 |
| 6 | 다이어그램 | 시나리오 기반으로 시각화 |

**핵심: 시나리오가 명확하면 다이어그램은 그냥 그려진다. 시나리오가 애매하면 다이어그램도 애매하다.**
