# 과잉 설계 점검

> 사이드 프로젝트가 "빅테크 운영 표준" 흉내 내다가 트래픽 대비 과한 도구를 짊어진 자리가 있는지 한 번 짚어보는 회고예요.

Phase 1~3 마치고 ADR 10개 + 실험 패키지 5개 + 운영 문서 (FAILURE-MODES, MULTI-INSTANCE, LIMITATIONS) + Grafana / Prometheus alert 까지 쌓고 보니까, "이게 다 필요했나" 가 자꾸 걸려서 적어둡니다.

## 과하다고 인정해야 하는 부분

먼저 솔직하게 — 일부 결정은 트래픽 대비 분명히 과해요.

**Resilience4j Circuit Breaker** 가 가장 의심 가는 자리예요.
현재 Redis 호출은 사용자당 송금 트랜잭션마다 1~2회밖에 안 일어나고, Redis 단일 노드의 P99 응답은 1ms 미만이에요.
이 트래픽이라면 CB 가 발화할 일 자체가 거의 없습니다.
그래도 들인 이유는 두 가지였어요 — (1) 코드 안에 "fallback 정책" 이 명시적으로 박혀 있어야 fail-open vs fail-closed 결정이 운영 옵션이 되고, (2) Redis 가 단일 노드라 (LIMITATIONS 1.2) 장애 시 cascading 가능성이 비현실은 아니에요.
다만 측정 없이 들인 부분은 인정합니다 — E3 실험이 NOT YET RUN 상태인 게 그 자리예요.

**ADR-010 의 Phase 4/5** 는 트래픽 100K TPS 가정인데, 우리 측정은 단발 VU=5 에서 멈춰 있어요.
30K, 100K 같은 숫자가 이 사이드 프로젝트의 현실과는 너무 떨어진 추정이라, 사실 ADR-010 의 Phase 4/5 는 "지금 결정" 이 아니라 "결정을 미리 박아둔 자리" 에 가까워요.
ADR 형식 자체가 "이 시점에 이 결정을 했다" 라는 기록인데, Phase 4/5 는 실제로 결정한 게 아니라 "그때 가서 어디로 갈지 미리 그려본 지도" 입니다.
이걸 ADR 로 묶은 건 형식 과잉이에요.
다음에 손볼 때 ADR-010 은 Phase 1~3 까지만 단정하고, Phase 4/5 는 ROADMAP 안의 미래 후보 섹션으로 옮기는 게 깔끔합니다.

**E3 / E5 실험 패키지** 가 NOT YET RUN 인데 DESIGN.md 가 250~280줄 분량이에요.
실측 데이터 없이 가설만으로 그 분량을 채운 건 형식 과잉이에요.
사이드 프로젝트의 실험 디렉터리가 측정 결과보다 두꺼운 설계 문서로 채워져 있으면, 이게 빅테크 흉내가 됩니다.
다음에 손볼 때 E3 / E5 의 DESIGN.md 는 핵심 가설 + 측정 변수 + 도구만 남기고 100~120줄 안쪽으로 정리하는 게 맞겠어요.

**FAILURE-MODES.md 의 컴포넌트별 시나리오 30+ 항목** 도 일부는 운영 환경에서 시뮬레이션 안 해본 가설들이에요.
"Postgres 디스크 풀 시 어떻게 회복" 같은 시나리오는 적어두는 가치는 있는데, 직접 안 겪어본 자리에서 "자동 회복 X / 수동 복구 Y" 라고 단정으로 적은 부분은 좀 부끄럽습니다.
다음에 손볼 때 검증된 항목과 가설 항목을 명시적으로 분리하는 게 맞아요.

## 과하지 않다고 보는 부분

반대로 들인 게 트래픽 대비 과한 게 아니라 적정선이었다고 보는 자리도 있어요.

**헥사고날 4계층 분리** (ADR-001) 는 트래픽 대비 무관한 결정이에요.
TPS 가 100이든 100K든 도메인 코드를 Spring/JPA 에서 분리하는 비용은 같고, 분리 안 한 채 시작했다가 나중에 분리하는 비용이 훨씬 큽니다.
이건 처음부터 들이는 게 맞아요.

**Outbox + 파티셔닝** (ADR-002/003) 도 1K TPS 미만에서도 필요한 자리였어요.
파티셔닝 없이 멀티 인스턴스 가면 빈 배치 1,658회 같은 자리가 나오고, 이건 트래픽 작아도 똑같이 나타납니다 (E1 실측).
단일 인스턴스에서는 안 필요했지만, Relay 자체가 SPOF 면 곤란하니까 멀티 인스턴스 + 파티셔닝은 적정.

**ELK + 분산 트레이싱** (ADR-006/007) 도 트래픽보다 운영 디버깅 가능성의 문제예요.
TPS 가 작더라도 traceId 못 따라가면 한 건의 송금 추적이 안 됩니다.
운영성은 트래픽 함수가 아니라 incident 함수.

**Testcontainers 통합 테스트** 도 작은 인프라 비용으로 큰 회귀 방어를 사주는 자리라 적정.

## 그래서 어디까지 줄일 건가

당장 손볼 자리는 세 곳이에요.

1. **ADR-010 의 Phase 4/5** 를 ROADMAP 안의 "후보" 로 옮기기.
   ADR 은 결정한 것만 적는 자리고, 결정 안 한 미래는 ROADMAP 으로.

2. **E3 / E5 DESIGN.md 분량 축소** — 가설 / 변수 / 도구만 남기고 100줄 안쪽.
   측정 없는 설계 문서가 두꺼우면 "흉내" 가 됩니다.

3. **FAILURE-MODES.md 의 시나리오에 "검증됨 / 가설" 라벨 추가**.
   직접 안 겪은 자리는 가설로, 겪은 자리는 검증됨으로 분리.

당장 안 손볼 자리도 적어둘게요.

- Resilience4j CB 는 코드 라인 작고 fallback 정책 명시화 가치가 있어서 일단 유지.
  E3 실측하고 나서 "역시 과했다" 가 잡히면 그때 빼는 게 맞아요.
- ADR 1~8 은 트래픽 무관하게 들어간 결정이라 유지.
- 다이어그램 15장은 README + 회고에 임베드된 자리가 명확하고, 한 장씩 보면 분량 부담이 크진 않아요.

## 회고의 회고

이 점검 자체가 늦었어요.
ADR 10개를 다 쓰고 실험 패키지 5개를 다 쓴 다음에 "과한가" 를 묻는 거랑, ADR 3개 쓸 때 묻는 건 다른 문제입니다.
형식이 먼저 쌓이고 나면 그걸 줄이는 게 더 큰 작업이 돼요.
다음 phase 부터는 ADR / 실험 패키지를 추가할 때마다 "이게 트래픽 대비 적정인가" 한 줄을 같이 적어두는 게 맞겠어요 — 결정 자체의 회고를 미루지 않게.
