# E2 — 락 전략 회귀 실험: 낙관락 → 비관락

> 작성 시점: 2025-11-23. 단일 머신, 단일 Transfer API 인스턴스, Postgres 한 대 기준.
> 이 문서는 실험 설계만 다룬다. 실측 결과와 회고는 `RESULTS.md`, `RETRO.md`를 본다.

---

## 1. 배경

송금 도메인에서 동시성 제어는 두 자리에서 갈린다.

- 같은 계좌에 동시에 출금/입금이 들어왔을 때 잔액 정합성을 어떻게 지킬 것인가.
- 트랜잭션이 충돌했을 때 어디까지가 클라이언트의 실패로 노출되어야 하는가.

Phase 1 직전까지 `AccountBalanceJpaEntity`는 JPA `@Version` 기반 낙관락만 사용했다. 충돌 빈도가 낮으면 가장 싸고, 락 대기도 없다. 그래서 처음에는 적합한 선택처럼 보였다.

그런데 `simple-test.js` (VU=5, 10s)를 돌리자 에러율이 80%로 찍혔다. 5명만 들어와도 절반 이상이 `StaleObjectStateException`으로 떨어졌다. 송금 API는 본질적으로 동일 계좌에 쓰기가 몰리는 도메인이라, 낙관락이 가정하는 "충돌은 드물다"가 깨졌다고 봤다.

이 실험은 그 가설을 확인하기 위한 것이다. 단순히 비관락이 더 좋다는 결론을 내려는 게 아니라, **언제 어떤 비용을 감수하고 비관락으로 가야 하는가**를 수치로 남기는 것이 목표다.

---

## 2. 문제 정의

| 항목 | 내용 |
|---|---|
| 대상 코드 | `services/transfer/application/.../TransactionService.kt#createTransfer` |
| 관측된 증상 | VU 5에서도 `Row was updated or deleted by another transaction` 80% 발생 |
| 가설 원인 | `@Version` 충돌 → JPA가 예외를 던지고 트랜잭션 전체 롤백 |
| 의심되는 부작용 | 재시도 없이 클라이언트에 500 노출, 사실상 throughput 1/5 수준 |

낙관락은 충돌 시 재시도를 전제로 한다. 그런데 우리 코드는 컨트롤러 레벨에서 재시도를 두지 않았다. 즉 "낙관락 + 재시도 없음" 조합이 도미노로 무너진 것이다. 여기에는 두 갈래 길이 있다.

1. 낙관락을 유지하고 재시도/백오프를 도입한다.
2. 비관락(`SELECT ... FOR UPDATE`)으로 전환해 DB 레벨에서 직렬화한다.

이 실험은 (2)의 효과와 비용을 측정한다. (1)은 `RETRO.md`의 후속 실험 후보로 남긴다.

---

## 3. 가설

### H1 — 에러율은 비관락이 압도적으로 낮다

VU ≥ 5 동일 조건에서 비관락의 HTTP 에러율은 낙관락 대비 **최소 50%p 이상** 낮다.

근거: 비관락은 락 획득 이전에 대기로 흡수하므로, `@Version` 충돌이 발생할 시간 창 자체가 사라진다. 충돌이 사라지면 클라이언트 실패도 사라진다.

### H2 — Latency 비용은 받아들일 수 있는 수준

비관락 도입 후 평균 latency 증가폭은 낙관락 대비 **100% 이내**, p95는 **100% 이내**.

근거: 락 대기 자체는 트랜잭션 길이의 함수다. 단일 송금 트랜잭션이 짧다면(수십 ms), 대기 시간도 그 배수 안에서 끝난다. 만약 100%를 초과하면 비관락이 직렬화 병목으로 작동한다는 신호다.

### H3 — 비관락은 데드락을 도입하지만, 정렬된 락으로 차단된다

A→B 송금과 B→A 송금이 동시에 들어오면 비관락은 원리적으로 데드락을 만든다. 그러나 `loadUsers`가 계좌번호 오름차순으로 락을 잡는 한, 모든 트랜잭션이 동일 순서로 락을 요청하므로 데드락은 발생하지 않는다.

이 가설은 **반례 검증** 성격이다. 비관락의 가장 흔한 함정을 우리가 피해 갔는지를 확인한다.

## 4. 변수

### 4.1 독립 변수 (조작)

| 변수 | 값 | 비고 |
|---|---|---|
| 락 전략 | 낙관락(`@Version`) / 비관락(`PESSIMISTIC_WRITE`) | 비교 대상 |
| 가상 사용자 수 | 5 (실측), 10/25/50/100 (계획) | k6 `simple-test.js`, `vus-*.js` |
| 계좌 풀 크기 | 송금자 20 / 수신자 20 | 충돌 확률 통제 |
| 송금 패턴 | 랜덤 / 핫스팟 단일 계좌 / 양방향 | `simple` / `hotspot` / `bidirectional` |

### 4.2 종속 변수 (측정)

- HTTP 에러율 (`http_req_failed`)
- 평균/median/p90/p95 latency
- `StaleObjectStateException` 발생 수
- 데드락 감지 수 (`bidirectional-test.js`의 `deadlock_errors`)
- (관찰) DB connection pool 점유율

### 4.3 통제 변수

- DB connection pool: HikariCP maximumPoolSize=10 (변경 없음)
- Transfer API 인스턴스: 1 Pod 고정
- 네트워크: localhost (네트워크 지연 제거)
- k6 실행 머신: 로컬 (Transfer API와 동일 머신)
- 트랜잭션 격리 수준: `READ_COMMITTED` (Postgres 기본)

## 5. 실험 절차

### 5.1 셋업

1. `docker compose up -d postgres kafka` — DB와 Kafka 기동.
2. 초기 데이터: 송금자 계좌 20개(잔액 충분), 수신자 계좌 20개.
3. Transfer API 단일 인스턴스 부팅.

### 5.2 시나리오

각 시나리오를 두 락 전략에서 동일하게 실행한다.

| 시나리오 | k6 파일 | VU | duration | 검증 의도 |
|---|---|---|---|---|
| baseline | `simple-test.js` | 5 | 10s | 최소 부하에서 충돌 빈도 |
| ramp | `load-test.js` | 10→100 | 5m | VU 증가에 따른 곡선 |
| hotspot | `hotspot-test.js` | 20→100 | 3m | 단일 계좌에 락 대기 누적 |
| bidirectional | `bidirectional-test.js` | 50 | 2m | 데드락 가능성 (H3) |

이번 회차에서 실측이 끝난 것은 `simple-test.js` 한 종이다. 나머지는 후속.

### 5.3 데이터 수집

- k6 stdout → `load-test/*.log`
- 서버 로그에서 `Row was updated or deleted`, `deadlock detected` grep
- 트랜잭션 응답 본문에 traceId 포함되므로, 실패 케이스의 traceId 보존

## 6. 성공 / 실패 기준

### 성공으로 간주하는 조건

- H1: 에러율 차이 ≥ 50%p
- H2: avg latency 증가율 ≤ 100% **그리고** p95 증가율 ≤ 100%
- H3: `bidirectional-test.js` 2분간 데드락 0건

### 실패로 간주하는 조건

- H2 위반: 비관락 도입 후 p95가 2배 이상 증가하거나 절대값이 500ms를 넘는다.
  → 비관락이 답이 아니라, 락 범위 축소 또는 분산 락 검토가 필요.
- H3 위반: `bidirectional-test.js`에서 데드락이 1건이라도 잡힌다.
  → `loadUsers`의 정렬 로직이 무효하거나, 다른 경로에서 락을 잡는 코드가 있다.

### 부분 통과 처리

H1, H3은 통과했지만 H2가 경계에 걸치는 경우(예: avg 증가 95%) → "감수 가능하지만 모니터링 필요" 등급으로 분류하고 후속 실험으로 넘긴다.

## 7. 위험과 한계

### 7.1 측정 한계

- 단일 머신 단발 측정이다. CPU/IO 다른 워크로드가 영향을 줄 수 있다.
- VU 5는 충돌 패턴 확인에는 적합하지만 throughput 절대값 해석에는 부적합하다.
- k6와 API가 같은 머신에서 돈다. 네트워크 비용은 제거되었지만 CPU는 공유된다.

### 7.2 일반화 한계

- 송금 패턴은 인위적이다. 실제 트래픽은 시간대별 핫스팟이 다르다.
- 계좌 풀 20개는 작다. 실 운영에서는 충돌 확률이 더 낮을 가능성이 크다.
- 인스턴스 1대 기준이다. 수평 확장 시 비관락의 직렬화가 어디까지 막아주는지는 별도 실험이 필요하다.

### 7.3 비관락 자체의 리스크

- 락 보유 시간이 길면 connection pool 점유가 늘어난다. 풀 사이즈 10에서 임계점을 넘으면 connection wait이 발생한다.
- 트랜잭션 안에서 외부 호출(예: 캐시, 이벤트 발행)을 하면 락 보유 시간이 늘어난다. 현재 코드는 캐시 갱신과 이벤트 발행을 모두 트랜잭션 안에서 한다.
- 데드락 회피는 `loadUsers`의 정렬 로직에 전적으로 의존한다. 다른 진입점에서 락 순서를 깨면 H3은 무효가 된다.

---

## 8. 무엇이 이 실험으로 결론나지 않는가

- "낙관락이 항상 나쁘다"가 아니다. 충돌이 드문 도메인에서는 여전히 더 싸다.
- "비관락이면 안전하다"가 아니다. 단지 송금 도메인의 충돌 패턴에 더 맞는다는 것까지만 말한다.
- 락 전략과 격리 수준의 상호작용은 다루지 않는다. 격리 수준은 `READ_COMMITTED`로 고정.
- 다중 인스턴스 환경에서의 분산 락 필요성은 별도 실험으로 분리한다.
