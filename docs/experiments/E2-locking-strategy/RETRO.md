# E2 — 락 전략 회귀 실험: 회고

> 작성 시점: 2025-11-23, 비관락 전환 직후. `DESIGN.md`와 `RESULTS.md`를 먼저 읽고 오는 게 낫다.

---

## 1. 가설은 맞았다. 그러나

H1, H2, H3 모두 통과로 적었다. 다시 보면 H1·H3은 확실히 통과, H2는 **통과로 부르기에 애매한 통과**다.

| 가설 | 처음에 잡은 기준 | 실측 | 통과 여부 | 솔직한 평가 |
|---|---|---|---|---|
| H1 | 에러율 -50%p 이상 | -62%p | 통과 | 압도적 통과 |
| H2 | latency +100% 이내 | avg +95%, p95 +90% | 통과 | 거의 천장 — 안전 마진 없음 |
| H3 | 데드락 0건 | 0건 (단, 양방향 시나리오 미실행) | 잠정 통과 | 정렬 락 효과는 별도 검증 필요 |

H2를 "100% 안에 들었으니 OK"로 보는 건 자기기만에 가깝다. VU 5에서 95%가 나왔다면, VU 50/100에서는 어떤 숫자가 나올지 모른다. 처음에 H2 기준을 "100%"로 잡은 것 자체가 너무 느슨했다. 실제로는 "VU별 곡선이 선형 이상으로 휘지 않을 것"이 더 의미 있는 가설이었다.

다음 실험에서는 H2를 다음과 같이 다시 잡는다.

> avg/p95의 VU 증가에 따른 곡선 기울기가 VU=5 → VU=50 구간에서 **5배 이상으로 휘지 않는다.**

## 2. 사후에 보이는 진짜 변수

이번 실험은 "낙관락 vs 비관락"으로 설계했다. 그런데 결과를 다시 보면, 비관락의 효과를 만든 결정은 락 모드 그 자체가 아니라 **계좌번호 정렬 락 획득 로직**이었다.

근거 둘.

1. 비관락만 적용하고 정렬을 빼면 양방향 송금에서 곧바로 데드락이 발생한다. 이 코드는 정렬 로직과 함께 도입되었기 때문에 따로 측정할 기회가 없었다.
2. `TransactionService.loadUsers`에 적힌 데드락 시나리오 주석(`TransactionService.kt:69-76`)이 가장 정확한 코드 다큐먼트다. 락 모드만 바꾸면서 정렬을 안 넣었다면 18% 잔여 에러가 아니라 잠금 타임아웃이 떴을 가능성이 크다.

즉 비관락은 **충분조건이 아니라 필요조건**이었고, 정렬 락이 **데드락을 안 만나게 한 결정타**였다. 두 변수를 독립적으로 측정하지 않은 것은 이 실험의 약점이다.

다음에 같은 종류 실험을 한다면 변수를 둘로 쪼개야 한다.

| 조합 | 데드락 | 에러율 (예상) |
|---|---|---|
| 낙관락 + 무정렬 | 낮음 | 매우 높음 (실측 80%) |
| 낙관락 + 정렬 | 낮음 | 높음 (정렬은 낙관락 충돌과 무관) |
| 비관락 + 무정렬 | 매우 높음 | 데드락 타임아웃으로 잡힘 |
| 비관락 + 정렬 | 0 | 낮음 (실측 18%) |

이 표의 (2)와 (3)을 직접 찍어보지 않았기 때문에, "비관락이 결정적"이라는 주장은 절반만 맞다.

## 3. 과소평가한 비용

### 3.1 Connection pool 점유

비관락은 락 보유 시간만큼 connection을 잡는다. 현재 송금 트랜잭션은 다음을 한 트랜잭션 안에서 한다.

- 두 계좌 락 획득 (`SELECT ... FOR UPDATE` × 2)
- 검증 (`TransferValidator`)
- 잔액 변경 + save (`userRepository.save` × 2)
- 트랜잭션 저장
- 캐시 갱신 (`dailyTransferAmountCache.addTodayAmount`)
- 이벤트 발행 (`eventPublisher.publishEvent`)

마지막 두 줄이 트랜잭션 안에 있는 게 의도된 설계인지 다시 점검해야 한다. 캐시는 트랜잭션 커밋 전이라도 over-estimate가 안전하다는 주석이 있다 (`TransactionService.kt:56`). 그러나 락 보유 시간이 늘어나는 비용은 별개다. 락을 더 빨리 풀면 같은 풀 크기로 더 높은 VU를 받을 수 있다.

### 3.2 잔여 18%의 정체

`@Version` 컬럼이 엔티티에 남아 있어 비관락 모드에서도 Hibernate가 버전 비교를 수행한다는 점은 사전에 명시적으로 분석되지 않았다. "락 모드만 바꾸면 충돌이 0이 된다"는 가정이 실제와 다르다. 이 사실은 실측 후에야 확인되었다. 다음 실험은 컬럼 제거 또는 사용 경로 통일로 잔여를 0으로 만들 수 있는지를 본다.

## 4. 후속 실험 후보

### E2-1 — Connection pool 크기 튜닝

| 항목 | 값 |
|---|---|
| 현재 | HikariCP maximumPoolSize=10 |
| 가설 | 비관락 환경에서 pool=10은 VU 50 근처에서 connection wait 임계점에 닿는다 |
| 측정 | pool 10/20/40, VU 50/100에서 `connection_wait_time`과 throughput |
| 성공 기준 | pool 2배 늘렸을 때 throughput 30% 이상 증가 또는 wait time 50% 이상 감소 |

### E2-2 — 격리 수준의 영향

| 항목 | 값 |
|---|---|
| 현재 | Postgres 기본 `READ_COMMITTED` |
| 가설 | `REPEATABLE_READ`로 올리면 비관락 잔여 18%가 줄어든다 |
| 측정 | 같은 `simple-test.js`, 격리 수준만 변경 |
| 위험 | `REPEATABLE_READ`에서 직렬화 실패(40001)가 증가할 수 있음 — 새 에러 유형 등장 |

이 실험은 매력적으로 보이지만, 격리 수준은 부작용이 광범위하다. 송금 외 다른 트랜잭션도 영향받는다. 우선순위는 E2-1보다 낮다.

### E2-3 — Redis Redlock 도입 시 비교

| 항목 | 값 |
|---|---|
| 가설 | 다중 인스턴스 환경에서 DB 락만으로는 한계가 있고, Redis 분산 락이 인스턴스 간 직렬화에 더 적합하다 |
| 측정 | Transfer API 2 Pod, Redis 단일 인스턴스. DB 락 vs Redlock의 에러율/latency |
| 비고 | 단일 인스턴스 환경에서는 의미 없음 — 실험 자체가 다중 인스턴스 셋업 비용을 동반한다 |

E2-3은 본격적으로 들어가기 전에 "단일 머신 DB 락이 어디까지 버티는가"부터 봐야 한다. 즉 E2-1을 먼저.

### E2-4 — 트랜잭션 범위 축소

| 항목 | 값 |
|---|---|
| 가설 | 캐시 갱신/이벤트 발행을 트랜잭션 밖으로 빼면 락 보유 시간이 줄고 throughput이 늘어난다 |
| 측정 | `simple-test.js` 동일 조건, 락 보유 시간만 변수로 측정 |
| 위험 | 캐시 일관성, 이벤트 누락 가능성 — `phase-1-outbox-and-partitioning.md`에서 다룬 문제와 다시 만난다 |

이 실험은 락 비용을 줄이는 가장 직접적인 카드다. 하지만 outbox 패턴과의 상호작용을 무시할 수 없다. 별도 설계 검토가 선행되어야 한다.

## 5. 무엇을 배웠나

### 5.1 가설은 맞아도 측정 범위가 좁으면 결론은 좁아진다

VU 5에서 통과한 가설은 VU 5에서만 유효하다. "비관락이 정답이다"라고 일반화하면 안 된다. 송금 도메인, VU 5, 단일 머신, 계좌 20개 환경에서 비관락이 낙관락보다 낫다 — 이게 이 실험이 말할 수 있는 전부다.

### 5.2 변수를 충분히 쪼개지 않으면 어떤 변수가 효과를 만들었는지 모른다

락 모드와 정렬 로직을 같이 도입했다. 효과는 두 변수의 합이다. 다음 실험은 한 번에 한 변수만.

### 5.3 "에러율 80%"는 코드 결함이 아니라 도메인-알고리즘 불일치였다

낙관락이 동작하지 않은 게 아니다. 송금 도메인이 낙관락이 가정하는 "충돌은 드물다"를 만족하지 않았을 뿐이다. 알고리즘이 도메인을 못 따라가는 경우, 알고리즘을 바꾸는 게 답이지 알고리즘을 더 빠르게 굴리는 게 답이 아니다.

### 5.4 측정은 끝났지만 실험은 끝나지 않았다

이 실험으로 "단일 인스턴스에서 비관락이 더 낫다"까지 갔다. 다음 질문이 줄줄이 남아 있다.

- VU 50/100에서 곡선은 어떻게 휘나
- pool 크기가 어디서 임계점을 만드나
- 다중 인스턴스에서는 어떤 락이 더 적합한가
- 트랜잭션 범위를 줄이면 락 비용이 얼마나 빠지나

각각이 E2-1 ~ E2-4의 후보다.
