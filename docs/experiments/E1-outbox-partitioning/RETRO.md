# E1 — Retrospective: 가설은 맞았지만, 가설이 다 보지 못했다

> 세 가설 모두 기준선을 통과했다. 채택 결정도 했다. 그런데 회고를 쓰는 이유는, 가설이 통과했다는 사실보다 "가설이 무엇을 놓쳤는가" 가 다음 실험을 만드는 재료이기 때문이다.

- **Experiment ID**: E1
- **Status**: Completed
- **Retro Date**: 2025-12-15

---

## 1. 가설이 맞았던 부분

**H1 — DB 쿼리 99% 감소**. 기준선 90% 를 크게 넘는 수치로 통과. "MOD 파티셔닝이 빈 배치를 제거한다" 는 메커니즘 자체는 정확히 예측대로 작동했다.

**H2 — 33.3% 균등 분배**. Snowflake event_id 의 단조 증가 특성을 알고 세운 가설이라 통과는 거의 결정론적이었다. 만약 ID 가 UUID 였다면 같은 가설을 세우지 않았을 것이다 — 분포가 균등하더라도 32 비트 정수 평균이 균등할지는 별도 검증이 필요했을 것이다.

**채택 판단의 비대칭성**. 비용은 단발 +2.33 초, 이득은 DB 부하·예측 가능성·확장성. 같은 단위로 비교할 수 없는 두 축에서 "어느 쪽에 가치를 둘 것인가" 가 핵심이라는 가설은 그대로 맞았다. 이건 측정 이전의 판단이지만, 측정 후에도 흔들리지 않았다.

---

## 2. 가설이 틀렸거나, 보지 못한 부분

### 2.1 H1 의 통과 폭은 가설의 모델이 정확해서가 아니라, 변수 하나가 빠져 있어서였다

원래 가설은 "쿼리 수 ≈ 처리한 배치 수" 라는 암묵적 모델에 기반했다. 그런데 실제로는 **빈 배치 1,658회**가 결과의 대부분을 만들었다. 가설 작성 시점에 빈 배치를 변수로 끄집어내지 못한 게 가장 큰 한계다.

이게 왜 문제인가. H1 의 통과 폭(99%)을 "MOD 가 그만큼 강력하다" 고 해석하면 다음 실험에서 같은 강도를 기대하게 된다. 그런데 실제 99% 의 대부분은 "SKIP LOCKED + 동일 쿼리 3대 경합" 이라는 Before 시나리오의 비효율에서 온다. **상대 비교의 큰 격차는 After 의 우월함이 아니라 Before 의 비효율에서 비롯될 수 있다.** 다음 실험에서는 비교 대상을 더 다양화해야 한다.

### 2.2 H3 는 단발 측정이라 통과 여부 자체가 운에 가깝다

+12.7% 라는 숫자는 기준선 15% 안에 들어왔지만, 만약 OS scheduling 이 0.5 초 더 흔들렸다면 +15.4% 가 됐을 수 있다. 한 번의 측정으로 임계치를 ±1%p 차이로 통과/실패 판정한 것은 **측정 설계가 결과에 비해 약했다는 의미**다.

이걸 처음부터 알았다면 다음 중 하나를 했을 것이다.

- 각 시나리오 N=10 회 반복, 중앙값과 IQR 로 비교.
- 또는 H3 의 기준선을 더 느슨하게(예: ≤ 25%) 잡고, 본 실험에서는 정확한 폭을 알아내는 데 집중.

### 2.3 "단발 머신 벤치의 처리 시간" 이 의사결정의 변수로 적합했는가

채택 결정에서 H3 (처리 시간) 의 비중은 사실상 낮았다. 그런데 가설 단계에서 H3 를 동등한 가중치로 다뤘다. 만약 처음부터 "단발 머신 벤치의 처리 시간은 정성적 신호로만 사용한다" 고 명시했다면, +12.7% 와 +14.7% 사이의 차이에 신경 쓰지 않아도 됐을 것이다.

가설 자체가 의사결정의 우선순위와 어긋났던 부분이다.

## 3. 사후에 알았으면 좋았을 변수

다음 변수들을 미리 측정에 포함하거나 통제했더라면 결과 해석이 훨씬 명확해졌을 것이다.

### 3.1 JIT warm-up

JVM 의 첫 1~2 초는 인터프리터 또는 C1 컴파일 상태에 가깝다. 본 실험은 Before/After 를 순차 실행했는데, 두 번째 실행은 JIT 가 더 데워진 상태에서 시작한다. **After 가 JIT 측면에서 유리한 출발선에 있었음에도 +12.7% 느렸다**는 것은 MOD 오버헤드의 실제 비용이 단발 측정값보다 클 가능성을 시사한다. 측정 순서를 무작위로 섞고 N 회 반복했다면 이 영향을 정량화할 수 있었다.

### 3.2 PostgreSQL buffer pool 상태

두 번째 실행은 첫 번째 실행이 만들어 둔 buffer pool warm 상태에서 시작한다. 인덱스 페이지가 메모리에 있는 상태에서의 측정과 cold start 측정은 결과가 다르다. 통제하려면 매 실행 전 `pg_buffercache` 를 확인하거나 PG 재시작이 필요하다.

### 3.3 빈 배치 폴링 사이의 sleep interval

Before 시나리오에서 Instance 2 가 1,658회 폴링한 18초 사이에는 polling 간 sleep 이 거의 없다 (`@Scheduled(fixedDelay)` 기본값 또는 즉시 재폴링). sleep interval 을 100ms / 500ms / 1s 로 바꿔보면 빈 배치 횟수가 어떻게 변하는지 후속 실험에서 측정할 가치가 있다. 이건 E1-3 로 분리했다.

### 3.4 MOD 함수 인덱스 효과

After 의 +12.7% 가 함수 인덱스로 얼마나 회수되는지는 측정하지 않았다. `CREATE INDEX ON transfer_events ((event_id % 3))` 를 추가하고 다시 측정하면 가능. 다만 ADR-003 에 적은 대로 **totalInstances 가 바뀌면 인덱스가 무용지물** 이라 운영 비용이 추가된다. 이 트레이드오프를 정량화하는 것은 별도 실험으로 분리할 가치가 있다.

## 4. 후속 실험 가설

본 실험이 닫지 못한 질문들을 후속 실험으로 옮긴다.

### E1-1 — 인스턴스 수 확장 시 선형성 유지 여부

- **질문**: N = 5, 7, 10 으로 늘려도 H1·H2·H3 의 결론이 유지되는가?
- **가설**: H2 (균등 분배) 는 유지되지만, H3 (처리 시간 오버헤드) 는 N 에 비례해 증가하지 않는다. MOD 의 비용은 N 과 무관하게 행당 상수이기 때문이다.
- **위험**: PostgreSQL 의 lock manager 가 N 증가에 따라 다른 병목을 드러낼 수 있다.

### E1-2 — 파티션 수 ≠ 인스턴스 수 시 동작

- **질문**: `totalPartitions = 12` 로 고정하고 인스턴스를 3대 → 4대 → 6대로 늘리면 어떻게 되는가?
- **가설**: 각 인스턴스가 여러 파티션을 담당하는 모델이 가능. 다만 인스턴스 추가/제거 시 파티션 재할당 로직이 필요하므로 ADR-003 의 "instance 수 변경 시 일시 정지" 제약이 완화될 수 있다.
- **연결점**: ADR-003 §Consequences 의 "단일 파티션 장애의 영향" 항목.

### E1-3 — 빈 배치 polling interval 튜닝

- **질문**: Before 시나리오에서 polling interval 을 늘리면 빈 배치 횟수가 정확히 어떻게 감소하는가?
- **가설**: interval = 1s 면 빈 배치 횟수가 10~20 회 수준으로 떨어진다. 즉 본 실험 결과의 H1 통과 폭이 인위적으로 부풀려졌을 수 있다.
- **의미**: 이 실험이 통과해도 MOD 파티셔닝의 정성적 이득(예측 가능성, 락 경합 제거) 은 그대로 유효. 다만 "쿼리 99% 감소" 라는 표현은 polling interval 의존적이라는 단서를 붙여야 한다.

이 세 실험은 본 실험과 변수 한 개만 다른 형태로 설계 가능하다. 그래야 변수의 효과를 분리할 수 있다.

## 5. 운영 적용 시 주의

[DECISIONS-TIMELINE Stage 5](../../DECISIONS-TIMELINE.md) 와 ADR-003 §Consequences 가 다루는 내용이지만, 실험 회고 관점에서 다시 정리한다.

### 5.1 인스턴스 수 변경 시 일시 정지 절차 필요

`totalInstances` 가 인스턴스마다 다르면 누락 또는 중복 발행이 발생한다. 본 실험은 3대 고정 환경에서만 검증했다. 운영 중 확장하려면 다음 절차가 강제된다.

1. 모든 PENDING 이벤트 소진 대기 (drain).
2. 모든 인스턴스 중단.
3. `totalInstances` 일괄 변경.
4. 재기동.

이건 단순 "그냥 한 대 더 띄우면 됨" 으로 끝나지 않는 운영 비용이다. E1-2 에서 가상 파티션 N=12 같은 방식을 검증하면 이 제약이 풀린다.

### 5.2 단일 파티션 장애 영향 범위

Instance 2 가 죽으면 `MOD 3 = 2` 인 이벤트가 정체된다. K8s liveness probe 와 자동 재시작이 일차 방어선이지만, 본 실험은 정상 상태에서의 분배만 측정했다. 장애 주입(chaos) 시나리오는 E4 (load-baseline) 와 연결될 수 있다.

### 5.3 모니터링 메트릭 정의

본 실험에서 "예측 가능성" 을 핵심 이득으로 채택했지만, 그 이득을 운영에서 실제로 회수하려면 다음 메트릭이 노출되어야 한다.

- 각 인스턴스의 분당 처리 건수 (gauge).
- 인스턴스 간 처리 분포 표준편차 (계산값).
- 빈 배치 횟수 / 분 (counter).

이 메트릭이 없으면 33.3% 균등 분배의 가치를 운영자가 인지할 수 없다. retrospective phase-1 의 §9 "남은 리스크" 항목과 직접 연결된다.

### 5.4 Outbox retention 부재

본 실험에서 다루지 않았지만, 발행 완료된 행이 계속 쌓이면 인덱스 효율이 떨어진다. MOD 파티셔닝의 효과는 PENDING 행 분포에 의존하는데, 전체 테이블이 커지면 ORDER BY event_id 의 비용이 함께 커진다. 본 실험의 +12.7% 는 테이블 크기 10,000 행 기준이라, 100만 행 / 1억 행 환경에서는 다른 분포가 나올 수 있다.

## 6. 이번 실험에서 학습한 것

요약하면 다음이다.

1. **가설은 변수 누락을 점검하는 절차 없이 세우면 모델이 성긴다.** "쿼리 수 = 처리한 배치 수" 라는 암묵적 모델이 실제 시스템 동작과 어긋나 있었다. 다음 실험에서는 가설을 세운 직후 "이 가설이 무시한 변수는 무엇인가" 를 한 줄로 적는 단계를 추가한다.

2. **단발 측정으로 ±1%p 차이를 임계치로 잡지 않는다.** N≥3, 가능하면 N=10 회로 잡고 중앙값/IQR 로 비교한다. 그게 불가능한 경우 임계치를 충분히 느슨하게 잡거나, 해당 가설의 의사결정 가중치를 낮춘다.

3. **상대 비교의 큰 격차는 우월함이 아니라 비효율에서 올 수 있다.** Before/After 비교에서 차이가 크면 After 가 강한 게 아니라 Before 가 약했던 것일 수 있다. 다음 실험에서는 비교 대상을 다양화한다.

이 세 가지를 다음 실험(E1-1, E1-2, E1-3) 설계 단계의 체크리스트로 가져간다.
