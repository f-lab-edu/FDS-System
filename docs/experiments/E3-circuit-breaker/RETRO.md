# E3 — Retrospective

> "코드는 들어갔는데 실험은 안 했다" 에 대한 회고.
> 실패한 실험이 아니라, **수행하지 않은 실험** 의 회고다.
> 작성 목적: 갭을 정확히 표현하고, 후속 실험의 진입점을 남긴다.

---

## 1. 무엇이 문제였는가

CB 코드를 먼저 넣고, 그 효과를 측정할 인프라는 뒤로 미뤘다. 그 결과 다음 상태가 됐다.

- 송금 API 의 코드 경로에는 `@CircuitBreaker` 가 붙어 있다.
- application.yml 에는 sliding-window, failure-rate, wait-duration 같은 숫자가
  적혀 있다.
- prometheus-alerts.yml 에는 `RedisCircuitBreakerOpen` 알림이 등록되어 있다.
- 그런데 **이 셋이 운영 상황에서 의도대로 맞물려 동작하는지는 모른다.**

이건 코드가 틀렸다는 얘기가 아니다. 코드는 합리적이다. 다만 "합리적이다" 와
"검증됐다" 가 다르다는 점을 인지하지 못한 채 다음 작업으로 넘어갔다.

## 2. 처음엔 왜 그렇게 판단했는가

기억나는 판단 경로는 이렇다.

- Redis 가 단일 노드라는 위험을 인지했다.
- Resilience4j 가 Spring Boot 와 잘 붙는다는 것을 알고 있었다.
- "어노테이션 + 설정값 + fallback 메서드" 의 작업량이 비교적 작았다.
- chaos 실험은 도구 도입 + 시나리오 작성 + 측정/해석까지 작업량이 크다.
- 따라서 코드를 먼저 넣고, 측정은 이후로 미뤘다.

이 판단 자체는 합리적인 면이 있다. 작은 작업부터 끝내는 것이 일반적으로
좋은 전략이다. 다만 **"미루기" 와 "안 하기" 가 동의어가 된다는 위험** 을 과소
평가했다. 시간이 지나면 다음 작업이 들어오고, 측정은 계속 뒤로 밀린다. 결과적으로
"CB 가 있다" 가 코드 상태가 아니라 **검증되지 않은 가정** 으로 굳어 버린다.

## 3. 어디서 생각이 뒤집혔는가

다음 두 가지가 분명해진 시점에 판단이 바뀌었다.

첫째, 면접/리뷰 상황에서 "CB 가 실제로 효과 있다는 걸 어떻게 알아요?" 라는
질문에 답할 근거가 코드 외에 없다는 것을 인정해야 했다. 코드를 읽으면 "그렇게
하면 동작할 것 같다" 까지는 가지만, 그게 측정된 사실이 아니다.

둘째, `FAILURE-MODES.md` 1.4 의 "fail-open 으로 한도 우회 가능, 회계 정정 필요"
가 운영 SOP 가 없는 상태로 적혀 있다. 측정이 없으면 SOP 도 못 만든다. 즉
chaos 실험의 부재는 단순히 "성능 숫자가 없다" 가 아니라 **운영 절차의 공백**
으로 직접 연결된다.

## 4. 그래서 지금은 어떻게 보는가

CB 는 측정 없이 도입하면 안 되는 컴포넌트다. 이유는 두 가지.

**숫자가 정책이다**. sliding-window-size=20, failure-rate=50%, wait=10s 는
운영 정책이다. 이 숫자가 적절한지 판단할 근거가 실측 외에 없다. 다른 곳에서
"보통 이렇게 쓴다" 의 평균값으로 시작은 할 수 있지만, 그게 우리 시스템에 맞는지는
별개다. 운영에서 알게 되면 늦다.

**fallback 의 의미가 정책이다**. fail-open 으로 0을 반환할지, fail-closed 로
예외를 던질지는 비즈니스 결정이다. 이 결정은 두 정책의 비용을 정량적으로
비교할 수 있어야 합리적으로 내릴 수 있다. 현재는 "fail-open 으로 갔다" 만 있고,
그 비용이 얼마인지의 측정이 없다.

이 두 가지 때문에 "코드 도입 + 측정 미수행" 의 조합은 운영 단계 진입 전까지는
허용할 수 있지만, 운영을 본격적으로 운운하는 시점부터는 부채다.

## 5. 빅테크 운영 표준과의 갭

부끄러움이 아니라 작업 목록의 의미로 정리한다.

| 항목 | 빅테크 표준 (관찰된 사례 수준) | 현재 프로젝트 | 갭 |
|---|---|---|---|
| chaos 테스트 인프라 | Toxiproxy / Gremlin / 자체 chaos 도구가 CI 의 일부 | 없음 | 인프라 전체 부재 |
| CB 설정 튜닝 근거 | 부하 + 장애 실험 기반 숫자 결정 | 라이브러리 디폴트 + 추정 | 실측 0회 |
| fail-open/closed 정책 | 정책 결정 문서 + 회계 정정 SOP | LIMITATIONS 에 한 줄 | SOP 부재 |
| Bulkhead | Redis CB 와 다른 의존성 격리 | 미적용 | 한 어댑터 장애가 thread pool 공유 시 다른 어댑터에 영향 가능 (미검증) |
| HALF_OPEN 의 실패 케이스 | 실험으로 검증 | 미검증 | 회복 도중 다시 장애 발생 시 동작 미관찰 |
| 알림 임계치 (`for: 30s`) | 운영 데이터 기반 조정 | 짧은 OPEN 은 알림 안 받음 | 의도된 정책인지 모름 |

이 표의 모든 항목이 "지금 당장 막아야 할 위험" 은 아니다. 다만 **빅테크 수준의
운영을 한다면 채워야 하는 항목** 들이다. 본 프로젝트는 학습/포트폴리오 맥락이므로,
"안 한 것" 을 명확히 표시하는 것이 "다 한 것처럼 보이는 것" 보다 낫다.

## 6. 후속 실험

### E3-1 — Toxiproxy 도입 후 C2~C5 시나리오 측정

가장 우선. DESIGN.md 의 시나리오 매트릭스를 실측으로 채운다.

- 작업: docker-compose 의 `chaos` profile 에 Toxiproxy 추가, spring `chaos` profile
  로 Redis host 를 프록시로 swap, k6 스크립트에 chaos 트리거 추가.
- 산출물: `RESULTS.md` 의 추정 칸을 실측으로 교체. 부족한 경우 Grafana dashboard
  스크린샷 + 해석.
- 예상 작업량: 1~2일.

### E3-2 — fail-closed 정책 비교 실험

`getTodayAmountFallback` 이 `0L` 대신 예외를 던지는 정책으로 바꿔서 같은 시나리오를
돌린다. 비교할 것:

- 송금 API 실패율 (fail-closed 는 100% 실패, fail-open 은 over-permissive 통과)
- 회계 위험 (fail-open 의 한도 우회 건수 vs fail-closed 의 거절 건수)
- 사용자 영향 (단순 거절 vs 한도 위반 후 사후 정정)

이 실험의 산출물은 **숫자가 아니라 정책 결정** 이다.
"어느 쪽으로 가느냐" 를 비즈니스/리스크 관점에서 정한다.

### E3-3 — Bulkhead 추가 후 격리 검증

Resilience4j 의 `@Bulkhead` 를 Redis 어댑터에 추가했을 때, **다른 어댑터(JPA,
Kafka 등) 호출이 Redis 장애의 영향을 받지 않는지** 확인한다.

현재는 Tomcat thread pool 을 공유한다. Redis 호출이 timeout 까지 대기하는 동안
thread 가 묶이면, 같은 thread pool 의 다른 요청도 영향을 받는다 — 가설.
Bulkhead 로 격리하면 이 전파가 끊어진다는 가설을 검증.

이 실험은 "CB 만으로 충분한가" 라는 더 큰 질문에 답하기 위해 필요하다.

### E3-4 (선택) — 멀티 인스턴스 CB 상태 독립성

Resilience4j 의 CB 는 인스턴스 로컬 상태다. 송금 API 가 2대로 늘어났을 때,
한쪽이 OPEN 이고 한쪽이 CLOSED 인 상태가 일시적으로 발생한다.
이게 사용자 입장에서 어떻게 보이는지 (load balancer 의 라우팅에 따라 일부 요청은
빠르고 일부는 느림) 측정.

순서상 멀티 인스턴스 운영을 본격적으로 시작하기 전까지는 우선순위 낮음.

## 7. 회고에서 끌어낼 일반 원칙

본 실험에서 일반화 가능한 교훈을 따로 정리한다. 다음번에 비슷한 컴포넌트를
도입할 때 같은 실수를 반복하지 않기 위함.

- **숫자가 들어간 설정은 측정과 같이 들어와야 한다.** sliding-window=20 같은
  임계값은 라이브러리 디폴트일지라도, 운영 정책으로 굳어지는 순간 검증 책임이
  생긴다.
- **fallback 은 "안전망" 이 아니라 "정책" 이다.** fail-open 을 택했다면 그 비용을
  추적 가능해야 한다. 메트릭이 노출되어 있다는 것과, 그 메트릭으로 회계 정정이
  가능하다는 것은 다른 문제다.
- **"미루기" 는 "안 하기" 와 동의어가 되기 쉽다.** chaos 실험처럼 도구 도입이
  큰 작업은 작업 자체를 PR 로 분리해서 마일스톤에 박지 않으면 사라진다.
- **검증 안 된 부분을 "검증된 부분" 처럼 말하지 않는다.** "CB 가 있다" 와
  "CB 가 효과 있다" 는 다른 진술이다. 면접/리뷰/문서 어디에서든 구분한다.
