# E4 — 부하 베이스라인 결과

## 0. 이 문서의 한계 먼저

먼저 인정해야 할 것이 있다.

`load-test/` 디렉토리에는 `vus-10.js`, `vus-25.js`, `vus-50.js`, `vus-100.js` 네 스크립트가 있지만
**해당 스크립트의 실행 로그는 저장되어 있지 않다**.
보관된 k6 로그 3종 (`k6-output.log`, `k6-detailed.log`, `test-output.txt`)은
모두 `simple-test.js` (VU=5, 10s) 실행 결과다.

따라서 이 문서에서 "측정"이라 부르는 부분은 두 종류로 나뉜다.

| 구분 | 출처 | 신뢰도 |
|---|---|---|
| 직접 측정 | simple-test 5VU × 3회 실행 | 인용 가능한 사실 |
| 외삽 | simple-test 결과를 VU 10/25/50/100 으로 추정 | 추정. 후속 실험에서 검증 필요 |

DESIGN의 H1~H4 가설은 simple-test 만으로는 절반밖에 답할 수 없다.
이 문서는 **답한 부분**과 **답할 수 없는 부분**을 구분해 적는다.

## 1. 직접 측정: simple-test 3회 비교

같은 스크립트(VU=5, 10s, sleep(1))를 서로 다른 시점에 세 번 돌린 결과다.
세 번이 다른 이유는 **그 사이에 락 전략이 바뀌었기 때문**이다.

### 1.1 원본 로그 인용

`k6-output.log` line 87~107 (2025-11-22 19:28, 낙관락 시절):

```

checks_succeeded...: 60.00% 60 out of 100
```

`test-output.txt` line 97~117 (2025-11-22 21:04, 전환 과도기):

```

http_req_duration..: avg=37.23ms p(95)=50.31ms  max=51.72ms
http_req_failed....: 38.00% 19 out of 50
http_reqs..........: 50     4.814183/s
```

`k6-detailed.log` line 97~117 (2025-11-23 03:01, 비관락 전환 후):

```
checks_succeeded...: 91.00% 91 out of 100
http_req_duration..: avg=37.07ms p(95)=75.96ms  max=79.18ms
http_req_failed....: 18.00% 9 out of 50
http_reqs..........: 50     4.814796/s
```

### 1.2 정리

| 시점 | 락 전략 | TPS | avg | p95 | 에러율 |
|---|---|---|---|---|---|
| 2025-11-22 19:28 | 낙관락 | 4.90 | 19 ms | 40.16 ms | **80%** |
| 2025-11-22 21:04 | 전환 중 | 4.81 | 37.23 ms | 50.31 ms | 38% |
| 2025-11-23 03:01 | 비관락 | 4.81 | 37.07 ms | 75.96 ms | 18% |

### 1.3 이 표가 말하는 것

세 가지가 동시에 보인다.

- **TPS는 거의 변하지 않았다 (4.9 ≈ 4.8)**.
  당연하다. `sleep(1)` 이 지배적이라 VU 5의 이론 상한이 ~5 TPS다.
  락 전략은 TPS의 상한을 결정하지 않고, **그 상한에 도달하기까지의 에러율과 응답 시간**을 결정한다.

- **avg는 19ms → 37ms 로 약 2배 증가했다**.
  비관락은 같은 행을 잡으려는 트랜잭션을 직렬화하므로, 충돌이 있을 때 두 번째 요청은 기다린다.
  이 18ms가 "직렬화 비용의 기저값" 이다 (ANALYSIS.md §3 의 진단과 일치).

- **에러율은 80% → 18% 로 큰 폭으로 줄었다**.
  하지만 0% 가 아니다. 18% 의 잔여 에러는 두 가지 가능성이 있다.
  (a) 일부 코드 경로가 여전히 낙관락을 사용 중 — ANALYSIS.md §1 가설.
  (b) 비관락 적용 후에도 `transactions_pkey` duplicate (snowflake ID 충돌) 가 남는다 — `k6-output.log` line 43, 71 에서 관측된 패턴.

  현재 로그만으로는 (a)와 (b)의 비중을 분리할 수 없다.

### 1.4 가설 검증 (부분)

| 가설 | simple-test 결과로 답할 수 있는가 | 결과 |
|---|---|---|
| H1 (선형 구간) | VU=5 한 점만으로는 곡선을 그릴 수 없음 | **미검증** |
| H2 (락 sublinear) | VU=5 도 이미 락 충돌이 압도적 | **부분 검증** — 락이 지배적임은 사실 |
| H3 (풀 한계 plateau) | VU=5 는 풀 크기 10 미만이라 풀 자체가 한계가 아님 | **미검증** |
| H4 (5xx < 1%) | 비관락에서도 18%. 기준 **미달** | **불합격** |

H4 가 깨졌다는 사실이 가장 무겁다.
"비관락 전환했으니 안정적이다" 라고 결론짓기에는 18% 가 남아 있다.

## 2. 외삽: vus-10/25/50/100 의 예상 곡선

> 아래는 simple-test 의 직접 측정 (4.81 TPS / VU 5 / sleep(1) / 비관락) 을 출발점으로 한 **추정**이다.
> 실측이 아니다.

### 2.1 출발점 (사실)

`sleep(1)` + 비관락에서 VU 5 의 한 요청 평균은 37ms.
이론적으로 TPS = VU × (1 / (sleep + req_time)) = 5 / 1.037 ≈ 4.82.
실측 4.81 과 거의 일치 → **모델이 sleep 지배 구간에서는 잘 맞는다**.

### 2.2 VU 10 (추정)

같은 모델 적용: TPS ≈ 10 / 1.04 ≈ 9.6.
단, 충돌 확률은 계좌 풀 20개 + VU 10 에서 같은 계좌가 동시에 잡힐 가능성이 비선형으로 늘어난다.
대략 p95 = 80~150ms, 에러율 = 5~15% 추정.

> H1 ("VU 10 까지는 선형") 의 검증 지점.
> 만약 실측에서 TPS < 8 이거나 p95 > 200ms 면, **선형 구간 자체가 존재하지 않는다**는 뜻이고
> 그건 비관락 + 작은 계좌 풀의 조합이 VU 10에서도 이미 sublinear 임을 의미한다.

### 2.3 VU 25 (추정)

순진한 모델: TPS = 25 / (1 + req_time) ≈ 24.
하지만 락 대기 큐가 깊어지면 req_time 자체가 늘어난다.
ANALYSIS.md §3 의 모델 — 최악 대기 = 락 유지 × (동시 VU - 1) — 을 적용하면
같은 계좌에 평균 1.25명이 동시에 들어올 때 평균 대기는 ~25ms 증가.

추정: TPS = 20~24, p95 = 200~400ms, 에러율 = 10~25%.

### 2.4 VU 50, 100 (추정 + 경계)

VU 50 에서 더 무거운 영향이 들어온다.

- HikariCP `maximum-pool-size = 10` (`application.yml` line 55).
- 비관락 대기 중인 트랜잭션은 커넥션을 점유한 상태로 기다린다.
- 동시 활성 트랜잭션이 10을 넘으면 나머지는 `connection-timeout = 3000ms` 대기 후 실패.

VU 50: 평균 활성 트랜잭션이 10을 자주 넘기는 구간으로 추정. p95 > 1000ms 가능.
VU 100: 풀 고갈이 자주 발생. TPS 가 VU 50 대비 증가하지 않거나 줄어들 가능성.

> 이 두 점이 **DESIGN의 H3 검증 지점**이다.
> 실측 시 보고 싶은 것:
> - `HikariPool ... Connection is not available, request timed out after 3000ms` 형태의 에러 비율
> - TPS 의 plateau 또는 회귀

### 2.5 외삽 곡선 요약 (추정)

| VU | 추정 TPS | 추정 p95 | 추정 에러율 | 주된 병목 (추정) |
|---|---|---|---|---|
| 5 (실측) | 4.81 | 75.96 ms | 18% | 비관락 직렬화 + 잔여 코드 경로 |
| 10 | 8~10 | 80~200 ms | 5~15% | 동일 |
| 25 | 20~24 | 200~400 ms | 10~25% | 락 큐 깊이 증가 |
| 50 | 30~45 | 500~1500 ms | 15~30% | 락 + Hikari 풀 점유 |
| 100 | 30~50 (plateau) | > 1500 ms | 20~40% | Hikari 풀 고갈, connection-timeout |

> 이 표는 가설이다. 실측이 아니다. 후속 실험에서 한 칸씩 채워야 한다.

## 3. 의외 발견

이건 simple-test 만 봐도 직접 보인 것들이다.

### 3.1 락 전략은 TPS 천장이 아니라 에러율 곡선을 바꾼다

당초 가설은 "비관락 = 응답 시간 증가, 낙관락 = 에러율 증가" 정도였다.
실제로는 **TPS 자체는 둘 다 거의 같았다** (4.90 vs 4.81).
sleep(1) 환경에서는 락 전략의 차이가 처리량이 아니라
"같은 처리량을 얼마나 깨끗하게 받아내는가"에서 드러난다.

이게 중요한 이유: TPS 만 보는 벤치마크는 **이 차이를 놓친다**.

### 3.2 snowflake ID duplicate 가 부하와 무관하게 나온다

`k6-output.log` line 43, 71 에서 같은 ID에 대한 PK 위반이 두 번 관측됐다.

```
duplicate key value violates unique constraint "transactions_pkey"
  Detail: Key (id)=(250568244983762944) already exists.
```

application.yml line 105-108 의 snowflake 설정:

```
id:
  snowflake:
    node-id: ${SNOWFLAKE_NODE_ID:1}
    max-clock-backward-ms: 10
```

같은 node-id 안에서 같은 ms 에 너무 많은 ID 가 발급되면 sequence 회전이 일어나면서 충돌 가능성이 있다.
VU 가 5밖에 안 되는데도 발생했다는 것은 **부하를 더 늘렸을 때 빈도가 커질 것**이라는 신호다.

> 이건 별도 실험으로 분리해야 한다 (ID 생성기 단위 테스트 + 클록 backward 시나리오).

### 3.3 비관락 전환 직후 18%는 "전환이 끝난 게 아니다"

ANALYSIS.md §1 은 18% 를 "전환 과도기" 로 설명한다.
하지만 측정 시점이 비관락 커밋 e6b1744 **이후** (2025-11-23 03:01) 인데도 18% 다.
이 숫자가 의미하는 바는 둘 중 하나다.

- 전환이 정말 부분적으로만 됐다 — 어떤 경로는 아직 낙관락.
- snowflake ID 충돌 같은 락과 무관한 5xx 가 베이스라인으로 깔린다.

후속 측정에서 5xx 응답의 **traceId 별 stacktrace 분포**를 봐야 답이 나온다.

## 4. 트레이드오프

### 4.1 단일 인스턴스의 천장은 얼마인가

명확한 수치를 답할 수 없다. 직접 측정한 최고 부하는 VU=5 인데
그 한 점만으로 천장을 추정하는 것은 무리다.

대신 **상한의 상한** 은 말할 수 있다.

- `sleep(1)` 기반 시나리오에서 TPS 의 이론 상한 = VU.
- VU 200 까지 들이부어도 (이건 stress-test.js 의 설계)
  요청 처리 시간이 100ms 라면 한 VU 가 초당 0.9 회 정도 → TPS 상한 ~180.
- 하지만 비관락 직렬화로 실제 처리 시간이 락 대기로 1초를 넘기 시작하면
  VU 증가가 TPS 증가로 이어지지 않는다.

**현재 측정으로 말할 수 있는 것은 "VU 5에서 5 TPS 가 나온다" 까지다.**

### 4.2 인스턴스 추가의 ROI

E2 의 비관락 전환은 **계좌 단위 직렬화** 다.
인스턴스를 2대로 늘려도 같은 계좌 락 경합은 줄지 않는다 (DB 락이 공유 자원이라).

따라서 인스턴스 추가의 효과는 다음 두 가지로 나뉜다.

- **CPU/스레드 한계 해소** — Tomcat thread, JVM heap 분산. 이건 효과 있다.
- **DB 락 경합 해소** — 효과 없다. 오히려 같은 DB 에 더 많은 클라이언트가 붙는다.

즉 **인스턴스 추가는 "CPU bound" 일 때만 ROI 가 있다**.
지금 우리 베이스라인은 lock-bound 라서, 인스턴스 추가 전에 **계좌 풀 확대 / 샤딩** 을 먼저 검토해야 한다.

이게 RETRO 에서 후속 실험으로 분리되는 이유다.

## 5. "왜 VU=100 이 stress 가 아닌가"

질문의 형태로 정리해 둔다.

운영 환경의 실제 송금 TPS 는 추정해 본 적이 있다 (수치는 정확하지 않다, 운영 데이터 확인 필요).
일반적으로 결제 API 의 평일 평균 TPS 는 수십 ~ 수백 단위.
이 베이스라인의 VU 100 = TPS 100 (sleep(1) 가정) 은 **운영 평균보다 살짝 위, 피크보다는 낮다**.

따라서 VU 100 을 "stress" 라고 부르는 것은 부정확하다.
- stress 의 진짜 의미는 **운영 피크의 2~3배 이상**.
- 이 베이스라인의 VU 100 은 **운영 평균을 견디는가** 의 시험에 가깝다.

진짜 stress 는 `stress-test.js` (VU 50 → 200, `sleep(0.1)` → 실효 부하 약 10배) 의 몫이다.
E4 는 stress 가 아닌 **선형성 시험** 이다. 이걸 혼동하면 측정 목적이 흐려진다.

## 6. 결론과 다음 행동

### 결론으로 말할 수 있는 것

- 비관락 전환은 에러율을 80% → 18% 로 큰 폭으로 낮췄다 (사실).
- 그래도 18% 는 운영 베이스라인으로 부족하다 (사실).
- TPS 곡선의 모양 — 어디서 꺾이는지 — 은 **아직 측정되지 않았다** (사실).

### 결론으로 말하지 못하는 것

- 단일 인스턴스의 최대 TPS.
- HikariCP 풀 크기 10 이 충분한지.
- 멀티 인스턴스의 ROI.

### 다음 행동 (이미 작성된 vus-*.js 활용)

```bash
for f in vus-10 vus-25 vus-50 vus-100; do
  k6 run load-test/${f}.js 2>&1 | tee load-test/${f}.log
done
```

실측 후 이 문서의 §2 표를 **사실 칸으로 갱신** 한다.
그때 비로소 H1~H3 가설을 평가할 수 있다.
