# E4 — 부하 베이스라인 설계

## 1. 배경

이 실험은 transfer-api **단일 인스턴스**가 어디서 무너지는지 측정하기 위해 만든다.
멀티 인스턴스 결정, 커넥션 풀 튜닝, DB 샤딩, 비동기 분리 같은 후속 의사결정의 **기준선**이 필요했다.

근거가 되는 직접 관측은 두 가지다.

- 커밋 `e6b1744` — 낙관락 → 비관락 전환을 부하 측정 중에 결정.
- 커밋 `8cf1ad7` — RestTemplate으로 TIME_WAIT 누적을 직접 재현.

즉 이 베이스라인은 "이만큼은 견딘다"를 증명하기 위한 게 아니라,
"어떤 부하 패턴에서 어떤 종류의 한계가 먼저 드러나는가"를 분류하기 위한 측정이다.

> 한계: 이 실험은 **k6와 transfer-api를 동일 머신(macOS, M1 Pro 12C / 32GB)** 에서 돌린다.
> 따라서 절대 TPS는 운영 환경에 그대로 옮길 수 없다.
> 의미가 있는 것은 **VU 증가에 따른 곡선 모양**과 **무엇이 먼저 깨지는가**다.

---

## 2. 가설

부하를 직선적으로 늘리면 다음 네 단계가 차례로 나타난다고 본다.

### H1 — 선형 구간 (VU ≤ 10)

`sleep(1)` 기반 시나리오에서 TPS ≈ VU 가 성립한다.
이때 단일 요청 처리 시간 < 1s 이고, 동일 계좌 충돌 확률이 낮아 비관락 대기가 거의 발생하지 않는다.

**예측**: TPS ≈ VU, p95 < 100ms, 에러율 < 1%.

> 검증 방법: `vus-10.js` 결과의 TPS가 9~10 사이, p95 < 100ms 이면 H1 성립.

### H2 — 락 경합으로 sublinear (VU 25 ~ 50)

송금 계좌 풀이 20개라 VU가 늘수록 같은 계좌를 동시에 잡는 확률이 빠르게 올라간다.
비관락은 같은 행에 대한 트랜잭션을 직렬화하므로, TPS 증가가 VU 증가보다 느려진다.

생일 문제와 같은 형태로 충돌 확률은 비선형으로 증가한다.
계좌 20개 / VU 25 기준, 어떤 순간에 둘 이상이 같은 계좌를 들고 있을 확률은 무시할 수 없다 (대략 수십 % 추정).

**예측**: TPS < VU, p95가 VU 10 대비 2~3배 이상 증가. 에러율은 여전히 < 5% 유지.

### H3 — 풀 한계로 plateau 또는 회귀 (VU 100)

전제 자원:
- HikariCP `maximum-pool-size = 10` (application.yml line 55)
- Tomcat thread 기본 200
- `connection-timeout = 3000ms` (line 57)

VU 100이 동시에 비관락 대기 + DB 커넥션 점유에 들어가면 풀 크기 10을 초과한 요청은
`connection-timeout` 3초 안에 커넥션을 얻지 못하면 즉시 실패한다.

**예측**: TPS가 VU 50 대비 거의 증가하지 않거나 오히려 감소.
p95가 1000ms를 넘는 구간 출현. `HikariPool ... Connection is not available` 형태의 에러 가능.

> 회귀가 안 보이면 두 가지 가능성이 있다.
> (a) `sleep(1)` 때문에 실효 부하가 낮아 풀이 포화되지 않았다.
> (b) 비관락 대기가 풀 점유보다 먼저 직렬화 병목이 됐다.
> 어느 쪽인지는 RESULTS에서 구분한다.

### H4 — 안정성 기준

모든 VU 레벨에서 **5xx 비율 < 1%** 이어야 운영 가능한 베이스라인이다.

> 이 기준은 simple-test 단계에서 이미 깨졌다. 낙관락 시절 5xx 80%, 비관락 전환 직후 18%.
> 따라서 H4는 **비관락 전환이 완료된 후의 vus-10~100 시점**부터 평가한다.

## 3. 변수와 측정

### 3.1 입력 변수

| 변수 | 값 | 이유 |
|---|---|---|
| VU 수 | 10, 25, 50, 100 | 4개 점으로 곡선 모양 추정 |
| think time | `sleep(1)` | 사용자 행동에 가까운 패턴. TPS ≈ VU 가정 가능 |
| 계좌 풀 | 송신 20 / 수신 20 | 의도적으로 작게 잡아 충돌 압력을 만든다 |
| 금액 | 10,000 KRW 고정 | 잔액 고갈 방지. 금액 분포는 변수에서 제외 |
| 시나리오 길이 | 30s ~ 1m | warm-up 누락. RETRO에서 다시 다룬다 |

> `sleep(1)`을 고른 이유: stress 가 아니라 **선형 구간 확인**이 1차 목표. think time 0 은 stress-test.js 가 따로 맡는다.

### 3.2 측정 지표

| 지표 | 출처 | 의미 |
|---|---|---|
| TPS | k6 `http_reqs ... /s` | 처리량 |
| p50 / p95 / p99 | k6 `http_req_duration` | 응답 시간 분포 |
| 에러율 | k6 `http_req_failed` | 5xx 비율 |
| iteration_duration | k6 summary | sleep 포함 한 사이클 길이. 비관락 대기 누적 여부 추정 단서 |

### 3.3 측정하지 못한 지표 (RETRO 항목)

- HikariCP active/idle (Prometheus `hikaricp_connections_active` 미수집)
- Tomcat busy thread (Actuator 메트릭 미연동)
- JVM GC (G1GC log 옵션 미적용)
- DB lock wait (`pg_stat_activity` 미스냅샷)
- Kafka producer queue

이들을 못 본 채로는 "왜 TPS가 거기서 꺾였는가"를 추정으로만 답할 수 있다.
RESULTS에 추정과 사실을 구분해서 적는다.

## 4. 성공 기준과 실패 기준

### 성공 기준 (베이스라인으로 인정)

- VU 10에서 H1 성립 (TPS ≈ VU, p95 < 100ms, 에러율 < 1%).
- 곡선의 꺾이는 지점(plateau / 회귀)이 식별 가능.
- 에러 종류를 락 경합 / 커넥션 풀 / 다른 원인으로 구분 가능.

### 실패 기준 (다시 측정)

- VU 10에서도 에러율이 5%를 넘으면 비관락 전환이 완료되지 않은 것이다 → 코드 점검 후 재측정.
- 모든 VU 레벨에서 TPS가 거의 같으면 sleep(1)이 지배적인 거다 → think time 줄여서 재측정.
- 측정 중 transfer-api가 OOM / 재기동 → 측정 무효.

## 5. k6 스크립트 매핑

| 가설 | 스크립트 | 기간 | 핵심 관찰 |
|---|---|---|---|
| H1 | `load-test/vus-10.js` | 30s | TPS = 10 ± 1, p95 |
| H2 | `load-test/vus-25.js`, `vus-50.js` | 각 1m | TPS / VU 비율 감소 곡선 |
| H3 | `load-test/vus-100.js` | 1m | TPS plateau 여부, 에러 형태 |
| H4 | 위 전체 | — | 5xx < 1% 유지 여부 |

모든 스크립트는 입력 분포가 동일하고 VU만 다르다.
이건 의도다. 같은 시나리오에서 **VU만 바꿔 곡선을 본다**는 게 이 실험의 통제 변수 설계다.

## 6. 이 베이스라인이 아닌 것

명시해 둔다. 이 실험이 답하지 않는 질문이 있다.

- **운영 환경 TPS 한계** — 동일 머신 실행이라 절대 수치는 운영과 다르다.
- **장시간 안정성** — 최대 1분짜리 측정으로 메모리 leak, GC pause 누적은 못 본다.
- **spike 내성** — ramp-up 없이 갑자기 100 VU 들이부었을 때 어떻게 되는지는 별도 시나리오.
- **멀티 인스턴스 효율** — 인스턴스 추가 ROI는 후속 실험 (E4-1).

이 네 가지는 RETRO에서 "측정하지 않은 것"으로 명시하고, 후속 실험으로 분리한다.

---

## 7. 다른 실험과의 관계

- **E2 (locking-strategy)**: 낙관락 → 비관락 전환 자체의 정합성 검증.
  E4는 그 결과로 받은 비관락 위에서 **부하 곡선이 어떻게 그려지는가**를 본다.
- **E1 (outbox-partitioning)**: 송금 이벤트 발행 경로의 partition 전략.
  E4의 TPS 한계가 outbox 처리량과도 연결되지만, 이 실험에서는 producer-side만 본다.
- **E3 (circuit-breaker)**: Redis 장애 시 차단 동작.
  E4의 정상 부하 측정과 분리한다.

---

## 8. 측정 후 해야 할 일

RESULTS에서 다음 세 가지를 분리해서 정리한다.

1. **사실** — k6 로그에서 직접 인용한 숫자.
2. **해석** — 그 숫자가 어떤 병목을 가리키는가.
3. **추정** — 측정하지 못한 자원(Hikari, GC 등)에 대한 가설.

이 셋을 섞으면 베이스라인이 아니라 그냥 인상기가 된다.
